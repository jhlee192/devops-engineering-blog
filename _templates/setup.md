## 작업 로그

<!-- status: wip 동안에만 있는 섹션. 글을 정리할 때 통째로 지운다. -->

날짜별로 덧붙이기만 한다. **문장을 다듬지 않는다.**
명령어는 `#` 주석을 달아 그대로, 에러는 원문 그대로 **그 자리에서** 붙인다. 나중에는 다시 못 찾는다.
이 로그도 저장소에 들어가므로 처음부터 마스킹해서 쓴다.

### YYYY-MM-DD

```bash
# 주석으로 왜 그렇게 했는지 한 줄. 이 주석이 나중에 본문 설명이 된다
실행한 명령어 그대로
```

**에러**

```text
에러 원문 그대로. 조치까지 같이 적어도 된다
```

**정한 것** — 방향을 고르거나 뒤집은 날에만. 매일 쓰는 칸이 아니다

## 왜 필요했나

도입 전에 뭐가 불편했는지. 이게 없으면 "그래서 왜?"가 남습니다.

## 후보와 선택

무엇을 검토했고 왜 이걸 골랐는지. 우리 환경의 제약(비용, 인력, 기존 스택)을
솔직하게 적으면 비슷한 처지의 독자에게 바로 도움이 됩니다.
중간에 선택이 뒤집혔다면 그 사실도 씁니다. 로그에 남아 있을 겁니다.

## 구축 과정

전체 절차를 나열하지 말 것. 공식 문서에 있는 건 링크로 넘기고,
**막혔던 지점과 문서에 없던 설정**에 집중한다.

```
핵심 설정
```

## 겪은 문제

구축 중 또는 운영하면서 터진 것들. 여기가 실제로 검색돼 들어오는 부분입니다.

## 결과

## 아쉬운 점
